### 失败、原因和解决方法

1. Ubuntu直接克隆GitHub持续约90秒没有进展。
   - 原因：Ubuntu到GitHub链路缓慢，未收到明确Git协议错误。
   - 处理：中止克隆；确认残留目录只有112 KiB的不完整 `.git` 后删除，改由Windows下载并通过完整bundle传入Ubuntu。
2. 第一次执行 `git bundle verify` 报 `need a repository to verify a bundle`。
   - 原因：校验在非Git目录执行，Git缺少检查前置对象所需的仓库上下文。
   - 处理：改为 `git -C <Windows裸仓库> bundle verify <bundle>`，确认包含完整历史且状态为 `is okay`。
3. Ubuntu设置 `main` 跟踪 `origin/main` 失败。
   - 原因：Ubuntu没有GitHub SSH密钥，也没有取得私有远端引用；本项目已经决定由Windows代推送。
   - 处理：Ubuntu不设置私有远端跟踪，保留 `origin` 地址作说明，实际同步使用bundle。
4. 第一次GitHub哈希核验被PowerShell误解析 `^{}`。
   - 原因：PowerShell将未正确引用的标签解引用表达式视为脚本块。
   - 处理：把每个ref参数放进单引号，再次查询成功。

三端基线最终一致：Ubuntu `main`、Windows裸仓库 `main`、GitHub `main`及标签解引用结果均为 `284b7154b4a8d447c494b1f41d0df2d68b00b909`。

## 2026-09-07：未经修改的Ubuntu构建审计

关键构建命令：

```bash

  -DCMAKE_PREFIX_PATH=/home/d508/.local/share/codex-envs/400w-qt-linux-v2
cmake --build build-baseline --parallel 8
```

构建失败于 `src/ncurses_display.cpp`：代码访问 `WINDOW->_maxx` 和 `WINDOW->_maxy`，而当前ncurses把 `WINDOW` 暴露为不完整类型。该写法依赖库内部实现，不是稳定API。修复为公开的 `getmaxx(window)` 与 `getmaxy(window)`，并对窄终端宽度做非负保护。

本阶段没有使用sudo。为形成标准系统开发环境，后续需要用户在Ubuntu执行：

```bash
sudo apt update
sudo apt install -y build-essential git cmake ninja-build libncurses-dev gdb strace file
```

修复 `WINDOW` 私有字段后，工程完成编译和链接。随后在伪终端中进行5秒受控运行，程序触发C++标准库断言：

```text
std::vector<Process>::operator[]: Assertion '__n < this->size()' failed
```

原因是显示层默认请求显示10个进程，而教学骨架的 `System::Processes()` 尚未填充任何对象，循环仍访问 `processes[i]`。修复为 `min(请求数量, 实际容器大小)`，保证未完成解析器时也不会越界。该保护只解决显示层安全性，不代表进程采集已经实现。

构建后的 `file` 检查无法执行，因为Ubuntu系统尚未安装 `file` 命令；这不会影响链接。`ldd`确认程序当前依赖Qt独立环境中的ncurses、tinfo、form、libstdc++与libgcc，说明后续仍应建立标准系统工具链，避免把本项目绑定到Qt环境。

### 补丁应用过程中的失败记录

为保持Ubuntu为唯一工作仓库，Windows只生成补丁文件并通过SCP传入Ubuntu；每次先检查，再正式应用：

```powershell
scp .\stage1_ncurses_compat.patch ubuntu20-vm:/tmp/stage1_ncurses_compat.patch
scp .\stage1_runtime_guard.patch ubuntu20-vm:/tmp/stage1_runtime_guard.patch
```

```bash
cd /home/d508/projects/RK3588_System_Monitor
git apply --check /tmp/stage1_ncurses_compat.patch
git apply /tmp/stage1_ncurses_compat.patch
git apply --check /tmp/stage1_runtime_guard.patch
git apply /tmp/stage1_runtime_guard.patch
```

手工生成的两个补丁首次检查均报告 `corrupt patch`，其中运行时保护补丁在修正一次后又暴露出下一处hunk计数错误。

- 真实原因：统一diff的hunk头中，旧文件和新文件的行数统计与实际正文不一致，补丁语法本身不完整；这不是C++源码错误。
- 解决方法：逐段重新计算 `@@ -旧起点,旧行数 +新起点,新行数 @@`，每次都先运行 `git apply --check`。只有检查通过后才执行 `git apply`，因此失败尝试没有改动Ubuntu工作树。
- 工程经验：跨机器传递小规模源码修改时，补丁便于审查；但补丁文件也必须作为输入制品校验，不能跳过 `--check`。
- 收尾补丁首次检查也在文件末尾报告 `corrupt patch at line 69`，原因仍是新增段落的hunk行数少算；重新按带前缀的实际行数核对后修正。该次检查同样发生在正式应用之前。

## 2026-09-07：恢复VS Code到RK3588的Remote-SSH连接

### 失败现象

在VS Code的Remote-SSH列表选择 `tl3588` 后连接失败。命令行复现：

```powershell
ssh -vv -o ConnectTimeout=5 -o BatchMode=yes tl3588 "hostname"
```

连接尝试仍指向 `192.168.1.114:22`，最终报 `Connection timed out`。

### 真实原因与修复

开发板重新获取DHCP地址后，当前 `eth0` 地址已变为 `192.168.1.116/24`，但Windows的 `C:\Users\31379\.ssh\config` 仍保存旧地址。用短超时SSH直接验证 `.116` 后，确认远端主机名为 `RK3588-Tronlong`、架构为AArch64，并且ED25519主机密钥与原 `.114` 记录完全一致。

将配置改为：

```sshconfig
Host tl3588
  HostName 192.168.1.116
  HostKeyAlias 192.168.1.114
  Port 22
  User root
```

`HostKeyAlias` 让新IP继续使用已经验证过的旧板卡身份记录。没有使用 `StrictHostKeyChecking no` 绕过校验，避免把未知设备误当成开发板。

地址修正后第一次普通连接报告 `Host key verification failed`，原因正是known_hosts按旧IP索引；加入上述已验证的 `HostKeyAlias` 后解决。最终命令：

```powershell
ssh -o ConnectTimeout=5 -o BatchMode=yes tl3588 `
  "hostname; uname -m; ip -br address show eth0; pwd"
```

返回 `RK3588-Tronlong`、`aarch64`、`192.168.1.116/24`和`/root`，连接验证通过。

曾尝试用 `Test-NetConnection` 依次扫描多个候选地址，但该命令对每个不可达地址等待较久，批量任务在只完成第一个地址后达到30秒工具等待上限。该现象只是扫描方法效率低，不能作为开发板离线证据；改用已知候选地址配合SSH `ConnectTimeout=5` 后快速完成定位。
